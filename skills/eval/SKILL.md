# 평가

개발이 끝난 작업을 **처음 보는 눈으로 읽고** "잘 만들었나"를 판단한다. 끝나면 평가 기록(`eval-NN.md`)이 남는다.

지금 이 문서를 읽는 쪽이 평가자다. **이 문서를 따르는 동안에는 다른 계획·개발·검토 도구(다른 플러그인의 skill 포함)를 부르지 않는다.**

## 지키는 약속

- **새 세션에서 한다.** 이 세션에서 이 작업을 개발했다면 멈추고, 새 창에서 다시 부르라고 알린다. 구현 과정을 아는 눈은 새 눈이 아니다.
- **자동 메모를 끈 세션에서 한다.** Claude Code는 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`을 붙여 연 창이다(README). 이 세션의 맥락에 앞 세션들이 남긴 자동 메모가 보이면 멈추고, 메모를 끈 새 창에서 다시 부르라고 알린다. 사용자가 그대로 하라고 하면 메모의 내용은 판단 근거로 쓰지 않고, 기록 첫머리에 "자동 메모가 켜진 세션"이라고 적는다.
- 대화가 아니라 저장소에 남은 것만 읽는다.
- 제품 코드, 테스트, 설정을 고치지 않는다. 테스트를 돌리지 않는다(돌리는 것은 검수가 한다). 명령은 읽기용 git 명령만 쓴다.
- 쓰는 곳은 이 작업의 작업 폴더(`.harness/artifacts/work/<작업 이름>/`)뿐이다: `eval-NN.md`, 진행표(`INDEX.md`), 그리고 할 일을 더할 때 `tasks.json`과 `tasks/`.
- 진행표 맨 위의 `상태` 줄은 바꾸지 않는다. 개발은 그 줄이 "확정"일 때만 시작한다.
- 실패 메시지, 비밀값, 개인정보는 기록에 옮기지 않는다.

## 읽는 것

- 설명서(`spec.md`): 완료 기준, 이번에 안 할 것
- 할 일 목록(`tasks.json`)과 진행표(`INDEX.md`): 개발 때 남은 "권장"
- 저장소 규칙: `.harness/README.md`와 거기 적힌 규칙 문서
- 프로그램 기록(`state.json`)의 `baseline.head`: 작업을 시작한 커밋
- 진행표와 프로그램 출력에 적힌 시작 전 검증(`preflight`)의 결과. 평가는 `preflight`를 돌리지 않고, 적힌 것만 이렇게 읽는다.
  - `product`만 완료 증거로 읽는다. 그것도 프로그램의 check 기록(`state.json`, `checks/`)이 함께 있을 때만이다.
  - `aux: incomplete`는 보조검증이 끝나지 않았다는 뜻이다. 통과로 읽지 않는다.
  - `environment: blocked`는 통과가 아니다. 그 환경에서 낸 결과는 판단 근거로 쓰지 않는다.
- 이전 평가 기록(`eval-*.md`)은 아래 3번까지 끝낸 뒤에 읽는다. 이전 판단에 끌려가지 않게 하려는 것이다.

## 순서

1. **기준 잡기.**
   - 진행표의 할 일이 모두 "완료"인지 본다. 아니면 멈춘다.
   - `git status --porcelain`에 작업 폴더 밖의 변경이 있으면 멈추고 사용자에게 알린다. 평가는 커밋된 코드로만 한다.
   - 시작 커밋은 `state.json`의 `baseline.head`, 평가 대상 커밋은 `git rev-parse HEAD`다. 둘 다 적어 둔다.
   - 볼 변경: `git diff <시작 커밋> <평가 대상 커밋> -- . ':(exclude).harness/artifacts/work/<작업 이름>'`

2. **영향 지도.** 바뀐 것마다 한 줄씩 표로 적는다.

   | 바뀐 것 | 종류 | 직접 쓰는 곳 | 영향받을 수 있는 기존 동작 | 더 따라간 경로 | 못 따라간 곳 | 테스트 |
   |---|---|---|---|---|---|---|

   - 종류: 함수, DB 필드, 설정, API 응답 모양, 함께 쓰는 데이터.
   - 직접 쓰는 곳을 저장소에서 찾고, 동작이 달라질 수 있는 경로를 더 따라간다. 끝까지 못 따라간 곳은 "못 따라간 곳"에 적는다.
   - 테스트 칸: 그 동작을 확인하는 테스트가 있음(파일과 이름) / 허술함(무엇이 빠졌는지) / 없음.

3. **점검표.** 여덟 관점마다 칸을 채운다. 칸은 `확인 대상 → 근거 → 판단` 순서로 쓴다. 근거는 파일과 줄, 완료 기준 번호, 규칙 번호다.

   | 관점 | 보는 것 |
   |---|---|
   | 맞는가 | 빠진 경우, 경계 값, 오류 처리 |
   | 안전한가 | 입력 검사, 권한, 비밀값, 개인정보. 결제, 권한, 개인정보, DB 구조 변경이 설명서에서 승인된 범위와 환경 안인가(승인 기록이 없거나 범위를 넘으면 지적) |
   | 기존 코드와 맞는가 | 영향 지도의 사용처, 데이터 모양, 호환 |
   | 비용 | 반복 호출, 끝없는 작업, 큰 메모리 |
   | 저장소 규칙 | 규칙 문서의 번호 |
   | 할 일끼리 | 겹치거나 어긋나는 곳 |
   | 테스트 전체 | 빠진 경우, 테스트와 구현이 같은 잘못된 가정을 하는 곳 |
   | 남은 권장 | 개발 때 남은 "권장"이 지금 보니 꼭 고칠 것인지 |

   판단은 넷 중 하나다: 문제없음(근거와 함께) / 지적 / 해당 없음(이유) / 확인 필요(검수에서 무엇을 확인할지). 읽어서 알 수 없는 것을 "문제없음"으로 채우지 않는다.

4. **이전 지적 대조.** 두 번째 평가부터 한다. 이전 기록의 꼭 고칠 것이 고쳐졌는지 하나씩 본다.

5. **지적 나누기.** 다섯 종류로 나눈다.

   | 종류 | 쓰는 법 |
   |---|---|
   | 구현 오류 (꼭 고칠 것) | 입력, 기대 결과, 지금 코드가 낼 결과, 근거(파일과 줄), 관련 완료 기준. 실행하지 않았으므로 "코드에서 도출한 예상 실패"라고 적는다. 실패하는 테스트로 쓸 수 있는 것만 여기에 넣는다 |
   | 필수 테스트 누락 | 설명서나 완료 기준이 요구한 경우인데 테스트가 없다. 테스트가 없다는 것만으로 동작이 틀렸다고 쓰지 않는다 |
   | 검수 확인 항목 | 기대 결과는 정해져 있고 실행해야 알 수 있는 것. 무엇을, 어떻게, 기대 결과 |
   | 질문 | 요구나 정책이 모호해서 기대 결과를 정할 수 없는 것 |
   | 권장 | 그 밖에 근거가 있는 의견. 취향 차이는 적지 않는다 |

6. **마무리.**
   - 1번 때와 그대로인지 본다: `git rev-parse HEAD`가 평가 대상 커밋과 같고, `git status --porcelain`에 작업 폴더 밖의 변경이 없어야 한다. 다르면 평가 결과를 버리고 멈춘다.
   - `eval-NN.md`(NN은 이전 평가 다음 번호, 첫 평가는 01)에 적는다: 날짜, 도구, 시작 커밋, 평가 대상 커밋, 영향 지도, 점검표, 지적, "테스트로 확인되는 것과 안 되는 것"(영향 지도의 테스트 칸에서), 다음 단계.
   - 진행표에 "평가" 절을 만들어(이미 있으면 그 아래에) 평가 번호, 결과 한 줄, 다시 받은 횟수를 적는다.
   - 아래 "다음 단계"대로 한 뒤 작업 폴더만 커밋한다: `git add <작업 폴더>`. `git add -A`와 `git add .`은 쓰지 않는다. 작업 폴더가 git 제외인 저장소면 올리지 않고(`-f`로 밀어 넣지 않는다) 그렇게 했다고 진행표에 적는다.

## 다음 단계

| 상황 | 할 일 |
|---|---|
| 구현 오류, 필수 테스트 누락, 질문이 모두 없음 | 기록에 "검수로"라고 적는다. 사용자에게 새 창에서 검수(`review`)를 부르라고 알린다. 검수 확인 항목은 기록에 남아 검수가 읽는다 |
| 설명서 범위 안의 구현 오류 | 아래대로 할 일을 더한다. 사용자에게 개발(`dev`)을 부르라고 알린다. 개발이 끝나면 새 창에서 평가를 다시 받는다 |
| 필수 테스트 누락 | 이번 판에서는 할 일로 만들지 않고 사용자에게 알린다. 테스트만 더하는 할 일은 개발의 실패 확인(구현 전에 실패해야 함)을 통과하지 못한다 |
| 설명서 범위 밖(새 정책, 새 요구) | 사용자에게 묻는다. 필요하면 계획부터 다시 한다 |
| 질문 | 평가를 끝내지 않는다. 사용자에게 묻고 답을 진행표에 적은 뒤 이어 간다 |

- **범위는 파일이 아니라 동작으로 판단한다.** 할 일 목록에 없던 파일이라도, 이번 변경 때문에 기존 동작이 깨졌다면 범위 안이다.
- **할 일 더하기.** `tasks.json`에 다음 번호로 더한다. `kind`는 `bug`, `criteria`는 관련 완료 기준, `allowed_files`에는 고칠 파일과 새 테스트 파일, `check_args`는 새 테스트만 고르는 인자다(형식은 계획 문서의 "할 일 목록"). 할 일 본문(`tasks/NN-이름.md`)에는 지적을 그대로 옮기고 맡은 완료 기준을 적는다. 정답 구현은 쓰지 않는다. 진행표의 할 일 표에 "대기"로 행을 더하고 "평가 NN에서 더함"이라고 적는다.
- **세 번 제한.** 평가를 다시 받는 것은 세 번까지다. 넘으면 멈추고 사용자에게 알린다.

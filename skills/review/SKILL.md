# 검수

평가를 받은 그 코드가 **설명서대로 다 됐는지** 마지막으로 확인한다. 끝나면 검수 기록(`review-NN.md`)이 남는다.

지금 이 문서를 읽는 쪽이 검수자다. **이 문서를 따르는 동안에는 다른 계획·개발·검토 도구(다른 플러그인의 skill 포함)를 부르지 않는다.**

## 지키는 약속

- **새 세션에서 한다.** 이 세션에서 이 작업을 개발하거나 평가했다면 멈추고, 새 창에서 다시 부르라고 알린다.
- **자동 메모를 끈 세션에서 한다.** Claude Code는 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`을 붙여 연 창이다(README). 이 세션의 맥락에 앞 세션들이 남긴 자동 메모가 보이면 멈추고, 메모를 끈 새 창에서 다시 부르라고 알린다. 사용자가 그대로 하라고 하면 메모의 내용은 판단 근거로 쓰지 않고, 기록 첫머리에 "자동 메모가 켜진 세션"이라고 적는다.
- 코드, 테스트, 설정을 고치지 않는다. 고칠 것이 나오면 기록해서 개발로 넘긴다.
- 쓰는 곳은 이 작업의 작업 폴더뿐이다: `review-NN.md`, 진행표(`INDEX.md`), 그리고 할 일을 더할 때 `tasks.json`과 `tasks/`. 진행표 맨 위의 `상태` 줄은 바꾸지 않는다.
- 실패 메시지, 비밀값, 개인정보는 기록에 옮기지 않는다. 원래 깨져 있던 테스트는 이름과 "같음 / 다름 / 모름"만 적는다.

## 시작 조건

마지막 평가 기록(`eval-NN.md`)의 다음 단계가 "검수로"여야 한다. 구현 오류, 필수 테스트 누락, 요구나 정책에 대한 질문이 남아 있으면 멈춘다. 기대 결과가 정해져 있고 실행만 남은 "검수 확인 항목"은 그대로 받는다.

## 순서

1. **프로그램 검수 검사.**

   ```
   <파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> review --work <작업 이름> --since <마지막 평가의 대상 커밋>
   ```

   - 프로그램은 이 문서 폴더에서 두 단계 위의 `bin/hb.py`다. `<파이썬>`은 개발 때와 같다(진행표에 적혀 있다).
   - 전체 검사를 돌리므로 오래 걸린다. 바탕 검사 기록(`checks/001-baseline.json`)의 `seconds`를 보고, 셸 도구의 제한 시간을 그보다 넉넉하게 주어 **앞에서(foreground) 돌린다**. 도구의 최대 제한 시간(Claude Code는 10분)보다 오래 걸릴 때만 백그라운드로 돌리고, 끝났다는 알림을 받기 전에는 대조로 넘어가거나 턴을 끝내지 않는다. 한 번 실행하고 끝나는 방식(`claude -p`)에서는 백그라운드 검사가 세션과 함께 끊긴다.
   - 출력의 마지막 줄이 판정(JSON 한 줄)이다. 프로그램이 보는 것:
     - 커밋되지 않은 변경이 없는가 (작업 폴더의 관리 기록은 빼고)
     - 할 일이 모두 완료됐나
     - 바탕 검사 커밋 → 평가 대상 커밋 → 지금 커밋으로 이어지나
     - 평가 뒤에 바뀐 것이 관리 기록뿐인가
     - 바탕 검사 뒤에 바뀐 파일이 할 일들의 허락된 파일 안인가
     - 전체 검사에서 새로 깨진 테스트가 없나
     - 할 일마다의 테스트가 이번에도 통과하나 (건너뛰었거나 사라져도 통과가 아니다)
   - 관리 기록은 작업 폴더의 `INDEX.md`, `state.json`, `checks/`, `logs/`, `eval-*.md`, `review-*.md`다. 설명서와 할 일 목록은 관리 기록이 아니다.
   - `verdict`가 `ok`가 아니면 아래 "막혔을 때"로 간다. 프로그램의 판정을 뒤집지 않는다.

2. **대조.** `ok`면 시작 전에 `git rev-parse HEAD`와 `git status --porcelain`을 적어 두고 아래를 한다.
   - **원래 깨져 있던 테스트**(출력의 `still_broken`): 바탕 검사 기록(`baseline_record`)과 이번 기록(`record`)이 가리키는 `logs/`의 보고서나 화면 기록에서 그 테스트의 실패 내용을 보고, 원인이 같은지 판단한다. 기록에는 이름과 "같음 / 다름 / 모름"만 적는다. 다름과 모름은 사람 확인으로 넘긴다. 로그가 없으면 모름이다.
   - **테스트 수**(출력의 `tests`): 전체 수가 줄었거나 건너뛴 수가 늘었으면 이유를 찾아 적는다(예: 할 일에서 일부러 지운 테스트). 모르면 사람 확인으로 넘긴다.
   - **완료 기준표.** 기준마다 증거 테스트의 코드를 읽고, 무엇을 넣고 무엇을 확인하는지 적는다. 증거로는 이번 실행에서 통과한 테스트만 쓴다(할 일의 테스트는 출력의 `tasks`에 있다). 원래 깨져 있던 테스트는 증거가 될 수 없다.

     | 기준 | 증거: 테스트 이름과 입증하는 조건 | 이번 실행 | 판정 |
     |---|---|---|---|
     | C2 할인 뒤 금액은 0원 이상 | `test_coupon_over_total`: 주문 10,000원·쿠폰 20,000원 → 결제액 0원 | 통과 | 충족 |

     판정은 충족 / 일부만 입증(빠진 조건을 적음) / 미충족 / 사람 확인 중 하나다.
   - **시작 전 검증의 기록**(진행표나 출력에 적힌 `preflight`의 `outcome`): 세 칸을 따로 읽는다. 완료 증거로 읽을 수 있는 칸은 `product`뿐이고, 그것도 프로그램의 check와 이번 review 기록이 함께 있을 때만이다. 완료 기준표의 증거는 위대로 이번 실행에서 통과한 테스트만 쓴다.
     - `aux: incomplete`는 보조검증이 끝나지 않았다는 뜻이다. 통과로 읽지 않는다.
     - `environment: blocked`는 통과가 아니다. 그 환경에서 낸 결과는 증거로 쓰지 않는다.
   - 설명서의 "이번에 안 할 것"이 섞여 들어가지 않았는지 본다.
   - 결제, 권한, 개인정보, DB 구조 변경이 있으면 진행표에 승인 기록이 있고 승인된 범위와 환경 안인지 본다. 승인 기록이 없거나 범위를 넘었으면 검수 통과로 하지 않는다. 아래 "막혔을 때"의 "검수 막힘(코드)"처럼 기록하고, 범위 밖일 때처럼 사용자에게 묻는다.
   - 평가가 넘긴 검수 확인 항목: 이번 실행 결과로 확인되면 "확인됨", 아니면 사람 확인으로 넘긴다.
   - 사람 확인 항목은 방법과 기대 결과까지 쓴다. 예: "5,000원 쿠폰을 적용한 뒤 결제 화면에 할인액 5,000원과 최종 결제액 15,000원이 보이는지".
   - 끝나면 적어 둔 두 값이 그대로인지 본다. 다르면 대조 결과를 버리고 멈춘다.

3. **기록과 마무리.**
   - `review-NN.md`(NN은 이전 검수 다음 번호, 첫 검수는 01)에 적는다: 날짜, 도구, 시작 커밋, 평가 대상 커밋, 검수 대상 커밋, 결과, 프로그램의 `summary` 그대로, 원래 깨져 있던 테스트 판단, 완료 기준표, 사람 확인 목록, "테스트로 확인된 것과 안 된 것"(평가의 영향 지도와 이번 대조에서), PR 본문 초안.
   - 진행표에 "검수" 절을 만들어(이미 있으면 그 아래에) 검수 번호와 결과를 적는다.
   - 작업 폴더만 커밋한다(`git add <작업 폴더>`, 작업 폴더가 git 제외면 올리지 않음). 올리기(push), 합치기, 배포는 하지 않는다. 사용자에게 결과를 보고한다.

## 결과

| 결과 | 뜻 | 다음 |
|---|---|---|
| 검수 통과 | 프로그램 검사, 대조, 사람 확인까지 끝났다 (사람 확인이 없으면 대조까지) | 사람이 올리고 합친다 |
| 자동 검수 통과 · 사람 확인 대기 | 사람 확인만 남았다 | 사용자가 목록대로 확인하고 결과를 알려 주면 `review-NN.md`에 누가, 언제, 결과를 적고 "검수 통과"로 바꾼다. 기대와 다르면 지적으로 적고 아래 "검수 막힘(코드)"처럼 넘긴다 |
| 검수 차단(환경) | 아래 표 | 환경을 고친 뒤 같은 `--since`로 검수를 다시 한다 |
| 검수 막힘(코드) | 아래 표 | 할 일 추가 → 개발 → 평가 → 검수 |

## 막혔을 때

| 프로그램의 판정 | 할 일 |
|---|---|
| 평가 뒤에 바뀐 것이 있음 | 평가부터 다시 받으라고 알린다 |
| 커밋되지 않은 변경, 끝나지 않은 할 일, 커밋이 이어지지 않음, 허락된 파일 밖이 바뀜 | 건드리지 않고 사용자에게 알린다 |
| `not_run`, `timeout` | 검수 차단(환경) |
| 새로 깨진 테스트, 할 일의 테스트가 통과하지 않음 | `logs/`의 화면 기록을 읽어 원인을 나눈다. DB 연결 실패, 도구 없음, 권한, 실행 중단이면 검수 차단(환경). 코드 문제면 검수 막힘(코드) |

- 막혔을 때도 `review-NN.md`에 결과(검수 차단(환경) 또는 검수 막힘(코드))와 프로그램의 판정을 적고, 진행표의 "검수" 절에 한 줄 남긴 뒤 작업 폴더만 커밋한다. 다시 할 때는 다음 번호로 새로 적는다.
- **검수 막힘(코드)** 은 평가와 같은 형식으로 적는다: 실패한 테스트 이름, 입력, 기대 결과, 실제 결과(값만 짧게, 비밀값이나 개인정보가 섞이면 적지 않음), 관련 완료 기준, 화면 기록 파일 이름. 설명서 범위 안이면 평가 문서의 "할 일 더하기"대로 할 일을 더하고 사용자에게 개발을 부르라고 알린다. 범위 밖이면 사용자에게 묻는다.
- 환경을 고치다가 코드, 테스트, 설정, 의존성이 바뀌면 프로그램이 "평가 뒤에 바뀐 것이 있음"으로 잡는다. 그때는 평가부터 다시 한다.
- 이번 판에서는 lint와 빌드를 검수에서 다시 돌리지 않는다. 개발이 커밋할 때마다 돌렸다.

# 계획

코드를 쓰기 전에 **무엇을 만들지**를 글로 정한다. 끝나면 승인된 설명서와 할 일 목록이 남는다.

지금 이 문서를 읽는 쪽이 "지휘"다. 지휘는 계획에서 제품 코드를 고치지 않는다.

**이 문서를 따르는 동안에는 다른 계획·설계 도구(다른 플러그인의 skill 포함)를 부르지 않는다.** 설명서와 계획 문서는 아래의 작업 폴더에만 쓰고, 다른 곳에 따로 만들지 않는다.

## 지키는 약속

- 제품 저장소의 `.harness` 폴더는 저장소가 주인이다. 하네스는 읽기만 한다.
- 하네스가 쓰는 곳은 한 군데다: `.harness/artifacts/work/<작업 이름>/`.
- 규칙 문서(`.harness/docs/*.yaml`)와 안내문은 고치지 않는다. 새 결정이 필요하면 설명서에 초안으로만 적는다.
- 문서와 코드가 어긋나면 한쪽을 고르지 않고 멈춰서 사용자에게 알린다.

## 이번 판이 다루는 범위

- 할 일의 종류는 **새 기능(feature)** 과 **버그(bug)** 둘뿐이다.
- 결제, 권한, 개인정보, DB 구조 변경을 건드리는 일은 설명서에 넷을 적는다: 영향(무엇이 달라지는지), 범위와 환경(어느 코드와 어느 환경까지인지), 확인 방법, 되돌리는 법. 사용자가 승인하면 그 범위와 환경 안에서 개발한다. 넷 가운데 빈 것이 있거나 승인이 없으면 멈추고 사용자에게 알린다.
- 이 승인은 개발에 대한 것이다. 실제 DB, 데이터, 비밀값, 운영 환경을 다루는 일(마이그레이션 적용, 데이터 수정, 비밀값 열람이나 변경, 운영 배포 등)은 허락하지 않으며, 이 하네스의 개발 흐름에서는 실행하지 않는다. 그런 일은 대상과 하는 일을 적어 따로 명시적으로 승인받고, 그 대상, 하는 일, 사용자의 승인 글을 `INDEX.md`에 적는다. 실행은 이 흐름 밖에서, 그렇게 따로 승인받은 방법으로 한다.
- 승인된 범위와 환경이 그대로면 다시 묻지 않는다. 범위, 환경, 위험이 달라지면 달라진 일을 하기 전에 고친 넷을 사용자에게 보여 주고 다시 승인받은 뒤, 설명서의 넷과 영향받는 할 일을 고치고 진행한다. 영향받는 할 일이 이미 시작됐으면 개발의 "할 일 하나의 순서" 1번부터 다시 한다.
- 승인 글을 `INDEX.md`에 적을 때 비밀값과 접속 정보(비밀번호, 토큰, 접속 문자열 등)는 옮기지 않고 빼거나 가린다.
- 저장소의 안내문이나 `CLAUDE.md`가 "사용자 승인 필수"라고 적은 파일은 할 일에 넣기 전에 사용자에게 묻는다.

## 순서

1. **읽기.** `.harness/README.md`를 먼저 읽는다. 거기 적힌 규칙 문서 가운데 이 작업에 필요한 부분과 `.harness/docs/checks.json`(검사 계약)을 읽는다. 검사 계약이 없으면 멈추고 알린다.
2. **초안 저장.** 작업 이름을 정한다(영문 소문자, 숫자, 하이픈). 작업 폴더를 만들고 `spec.md`를 "초안" 상태로 저장한다.
3. **대화로 채우기.** 다섯 가지를 채운다: 들어가고 나오는 것, 왜 만들고 성공을 어떻게 아는지, 제약, 이번에 안 할 것, 예외 상황. 예외 상황도 무엇이 일어나야 하는지를 결과로 적는다("~와 같은 방식으로 둔다"처럼 쓰면 읽는 쪽마다 다르게 읽는다). 이미 받은 자료에 답이 있으면 다시 묻지 않는다. 중요한 미정 사항만, 한 번에 하나씩 묻는다.
4. **완료 기준에 번호.** `C1`, `C2`처럼 붙인다. 확인할 수 있는 문장으로 쓰고, 기준마다 "무엇으로 확인할지"를 한 줄 적는다. 확인 방법을 적을 수 없으면 기준을 다시 쓴다.
5. **기존 결정과 대조.** 저장소의 결정 기록과 부딪치는 곳을 표시한다.
6. **할 일로 나누기.** 아래 "할 일 목록"의 형식으로 적는다.
7. **짝 맞추기.** 완료 기준마다 맡은 할 일이 있는지, 할 일마다 맡은 기준이 있는지 표로 확인한다. 빠진 것이 있으면 고친다. 짝이 맞는다고 내용이 충분한 것은 아니다.
8. **승인.** 사용자에게 요약, 애매한 점, 이번에 안 할 것을 보여 준다. 결제, 권한, 개인정보, DB 구조 변경을 건드리면 위의 넷(영향, 범위와 환경, 확인 방법, 되돌리는 법)도 보여 준다. 승인하면 `INDEX.md`에 상태를 "확정"으로 적고, 승인 날짜와 사용자의 승인 글을 그대로 적는다(비밀값과 접속 정보는 빼거나 가린다).
9. **작업 브랜치와 첫 커밋.** 저장소의 브랜치 이름 규칙을 따라 작업 브랜치를 만든다. **지금 있는 브랜치에서** 만든다(검사 계약이 들어 있는 브랜치여야 한다). 작업 폴더의 파일만 지정해서 커밋한다. `git add -A`는 쓰지 않는다. 사용자가 하던 다른 변경은 건드리지 않는다.

승인 전에는 9번으로 가지 않는다. 9번이 끝나면 개발(`dev`)을 시작할 수 있다고 알리고 멈춘다.

## 작업 폴더

```
.harness/artifacts/work/<작업 이름>/
├── INDEX.md          진행표. 상태(초안/확정), 승인 기록, 할 일별 진행, 막힌 곳
├── spec.md           설명서
├── tasks.json        할 일 목록 (프로그램이 읽는다)
└── tasks/NN-이름.md   할 일 본문 (구현자가 읽는다)
```

개발 중에 프로그램이 `state.json`, `checks/`, `logs/`를 더한다. `logs/`는 git에 넣지 않는다.

## 할 일 목록

`tasks.json`:

```json
{
  "work": "<작업 이름>",
  "tasks": [
    {
      "id": "01",
      "title": "한 줄 제목",
      "kind": "feature",
      "criteria": ["C1"],
      "allowed_files": ["<고칠 파일>", "<새 테스트 파일>"],
      "check_args": ["<새 테스트 파일>"]
    }
  ]
}
```

- `kind`: `feature` 또는 `bug`.
- `allowed_files`: 이 할 일에서 바꿔도 되는 파일. 테스트 파일도 여기에 넣는다. 가능한 한 파일 이름을 그대로 적는다.
- `check_args`: 이 할 일의 테스트만 고르는 인자(테스트 도구에 그대로 넘긴다). pytest와 jest는 테스트 파일 경로, gradle은 `--tests`와 테스트 클래스 이름, xcodebuild는 `-only-testing:<테스트 대상>/<묶음 이름>`이다. 비밀값은 넣지 않는다.

할 일 본문 `tasks/NN-이름.md`에는 이것을 적는다: 맡은 완료 기준, 먼저 끝나야 하는 할 일, 함수와 클래스의 모양, 지켜야 할 저장소 규칙의 번호. **정답 구현 전체는 쓰지 않는다.**

할 일은 작게 나눈다. 할 일 하나가 끝날 때마다 전체 검사를 한 번 돌리므로, 서로 얽힌 변경은 한 할 일에 둔다.

## 분량

| 크기 | 설명서 |
|---|---|
| 작은 버그 | 세 줄: 증상, 재현 방법, 완료 기준 |
| 보통 기능 | 한 장 |
| 큰 일 | 여러 작업으로 쪼개 각각 한 장 |

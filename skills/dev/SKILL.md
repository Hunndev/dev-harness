# 개발

계획(`plan`)이 만든 할 일을 **하나씩 순서대로** 끝낸다. "됐다"는 말이 아니라 프로그램이 직접 돌린 검사 결과로 판정한다.

## 역할

| 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 지휘 (지금 이 문서를 읽는 쪽) | 프로그램 실행, 판정 읽기, 진행표 기록, 커밋 | 직접 구현하지 않는다 |
| 구현자 (새 보조 AI `hb:implementer`) | 테스트 작성, 구현, 보고 | 커밋, 작업 폴더 수정, 완료 선언 |
| 검토자 (새 보조 AI `hb:reviewer`) | 읽고 지적 | 파일 쓰기, 명령 실행 |
| 프로그램 (`hb.py`) | 검사 실행, 판정, 기록 | 뜻이나 품질의 판단 |

구현자와 검토자는 부를 때마다 새로 시작한다. 앞의 대화를 모른다고 보고, 읽을 파일의 경로를 준다.

## 프로그램 부르는 법

프로그램은 이 문서 폴더에서 두 단계 위의 `bin/hb.py`다.

```
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> baseline --work <작업 이름>
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> check --work <작업 이름> --task <번호> --phase red
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> check --work <작업 이름> --task <번호> --phase green
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> done --work <작업 이름> --task <번호>
```

- `<파이썬>`은 그 저장소의 테스트가 도는 파이썬이다. 모르면 사용자에게 한 번 묻고 `INDEX.md`에 적어 둔다.
- 출력의 마지막 줄은 JSON 한 줄이다. `verdict`가 판정이다.

| verdict | 뜻 | 지휘가 할 일 |
|---|---|---|
| `ok` | 받아들임 | `summary`를 진행표에 그대로 적고 다음으로 |
| `stop` | 규칙에 걸림 | `reason`을 읽고 아래 "멈췄을 때"대로 |
| `not_run` | 검사가 실행되지 않음 | 통과가 아니다. 환경이나 명령을 확인한다 |
| `timeout` | 제한 시간을 넘김 | 통과가 아니다. 사용자에게 알린다 |

- `baseline`과 `check --phase green`은 전체 검사를 돌리므로 몇 분 걸린다. 백그라운드로 실행하고 끝날 때까지 기다린다. 기다리는 동안 다음 단계로 넘어가지 않는다.

## 시작할 때 (작업마다 한 번)

1. 작업 브랜치에 있는지, `INDEX.md`의 상태가 "확정"인지 본다. 아니면 멈춘다.
2. `baseline`을 돌린다. 작업 트리에 커밋되지 않은 변경이 있으면 프로그램이 멈춘다. 그 변경은 건드리지 않고 사용자에게 알린다.
3. `baseline`이 `ok`면 `summary`("원래 깨져 있던 것 N건")를 `INDEX.md`에 적는다.

## 할 일 하나의 순서

1. **테스트 쓰기.** 구현자를 부른다. 할 일 본문의 경로를 주고 "테스트만 쓰고 멈춘다"고 시킨다. 새 함수가 필요하면 빈 뼈대까지만 만들게 한다.
2. **실패 확인.** `check --phase red`. 테스트가 본문에서 실패해야 `ok`다. `ok`가 아니면 구현자가 테스트를 고치고 다시 받는다.
3. **테스트 읽기.** 검토자를 새로 부른다. 설명서, 할 일 본문, 테스트 파일, 실패 확인 기록(`checks/`)의 경로를 준다. "꼭 고칠 것"이 있으면 구현자가 테스트를 고치고 2번부터 다시 한다. "꼭 고칠 것"이 남아 있는 동안에는 4번으로 가지 않는다.
4. **구현.** 구현자를 부른다. "테스트는 이미 있고 실패 확인을 받았다. 테스트는 고치지 말고 구현만 한다"고 시킨다.
5. **통과 확인.** `check --phase green`. 프로그램이 넷을 본다: 실패했던 테스트가 통과하는가, 테스트가 그대로인가, 새로 깨진 것이 없는가, 바꿔도 되는 파일만 바뀌었는가.
6. **구현 검토.** 검토자를 새로 부른다. 설명서, 할 일 본문, 바뀐 파일 목록, 통과 확인 기록의 경로를 준다. 구현자의 "문제없음" 보고는 주지 않는다.
7. **지적 반영.** "꼭 고칠 것"이 있으면 구현자가 고치고 5번과 6번을 다시 한다.
8. **커밋.** 아래 "커밋하는 순서"대로 한다.

검토자를 부르기 전과 후에 아래 두 명령의 출력이 같은지 본다. 다르면 검토 결과를 버리고 멈춘다.

```
git diff HEAD | shasum
git status --porcelain
```

## 커밋하는 순서

1. `INDEX.md`에 이 할 일의 결과를 적는다(프로그램의 `summary` 그대로, 남은 "권장" 지적, 고쳐 다시 받은 횟수).
2. 이 할 일의 파일만 지정해서 올린다: `git add <파일> <파일>`. `git add -A`와 `git add .`은 쓰지 않는다.
3. `done`을 돌린다. `ok`가 아니면 커밋하지 않는다.
4. 작업 폴더를 올린다: `git add .harness/artifacts/work/<작업 이름>`.
5. 저장소의 커밋 메시지 규칙을 따라 커밋한다.

커밋 뒤에는 작업 폴더에 아무것도 쓰지 않고 다음 할 일로 간다. 합치기, 올리기(push), 배포는 하지 않는다.

## 운영 규칙 네 줄

1. 검사 결과는 이번 실행에서 새로 나온 것만 쓴다. 지난 실행의 결과를 옮겨 적지 않는다. 원래 깨져 있던 것과는 개수가 아니라 테스트 이름으로 견준다(프로그램이 한다).
2. 끊긴 뒤에는 지금 변경 상태(`git status`와 마지막 커밋)를 먼저 보고 이어 간다. 커밋되지 않은 할 일은 검사부터 다시 한다.
3. 사용자 파일은 커밋에 섞지 않는다. 로그는 git에 넣지 않는다.
4. 진행을 막는 지적은 "꼭 고칠 것"뿐이다. "권장"은 진행표에 적고 넘어간다.

## 그 밖의 규칙

- **통과 표시.** 원래 깨져 있던 검사가 있으면 "전체 통과"라고 쓰지 않는다. 프로그램의 `summary`("새로 깨진 것 없음, 원래 깨져 있던 것 N건")를 그대로 쓴다.
- **테스트 정정.** 구현 중에 테스트가 틀렸다는 근거가 나오면 구현자는 멈추고 보고한다. 지휘가 이유와 수정안을 사용자에게 보여 주고, 승인받으면 `INDEX.md`에 적은 뒤 1번부터 다시 한다. 할 일 하나에 두 번까지다.
- **세 번 제한.** 테스트를 고쳐 다시 받는 것(2번과 3번)은 할 일 하나에 합쳐 세 번까지, 지적 반영(7번)도 따로 세 번까지다. 지휘가 `INDEX.md`에 세어 적는다. 넘으면 멈추고 사용자에게 알린다.
- **쓰는 곳.** `.harness` 안에서는 이 작업의 작업 폴더에만 쓴다. `state.json`과 `checks/`는 프로그램만 쓴다.
- **범위 밖.** 설명서에 없는 일이 필요해지면 하지 않고 "막힌 곳"에 적은 뒤 사용자에게 묻는다.

## 멈췄을 때

| `reason`의 내용 | 할 일 |
|---|---|
| 커밋되지 않은 변경이 있음 | 건드리지 않고 사용자에게 알린다 |
| 준비 단계 오류, 전부 건너뜀, 실패한 테스트가 없음 | 구현자가 테스트를 고친다 (세 번 제한에 셈) |
| 테스트가 바뀜 | 구현자가 테스트를 되돌리거나, "테스트 정정"대로 승인받는다 |
| 새로 깨진 테스트가 있음 | 구현자가 구현을 고친다. 테스트를 약하게 고치지 않는다 |
| 바꿔도 되는 파일 밖을 고침 | 그 변경을 되돌리게 하거나, 할 일의 범위를 고칠지 사용자에게 묻는다 |
| 실패 확인 뒤에 커밋이 생김 | 멈추고 사용자에게 알린다 |
| 통과 확인 뒤에 코드가 바뀜 | 5번부터 다시 한다 |

## 끝나면

모든 할 일이 커밋되면 사용자에게 보고한다: 끝낸 할 일, 프로그램의 판정 요약, 남은 "권장" 지적, 하면서 막힌 곳. 막힌 곳은 `INDEX.md`에도 적는다.

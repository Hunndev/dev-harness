# 개발

계획(`plan`)이 만든 할 일을 **하나씩 순서대로** 끝낸다. "됐다"는 말이 아니라 프로그램이 직접 돌린 검사 결과로 판정한다.

**이 문서를 따르는 동안에는 다른 계획·개발·검토 도구(다른 플러그인의 skill 포함)를 부르지 않는다.** 순서와 규칙은 이 문서의 것만 따르고, 계획 문서나 기록을 작업 폴더 밖에 만들지 않는다.

## 역할

| 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 지휘 (지금 이 문서를 읽는 쪽) | 프로그램 실행, 판정 읽기, 진행표 기록, 커밋 | 직접 구현하지 않는다 |
| 구현자 (새 보조 AI `hb:implementer`) | 테스트 작성, 구현, 보고 | 커밋, 작업 폴더 수정, 완료 선언 |
| 검토자 (새 보조 AI `hb:reviewer`) | 읽고 지적 | 파일 쓰기, 명령 실행 |
| 프로그램 (`hb.py`) | 검사 실행, 판정, 기록 | 뜻이나 품질의 판단 |

구현자와 검토자는 부를 때마다 새로 시작한다. 앞의 대화를 모른다고 보고, 읽을 파일의 경로를 준다.

## 프로그램 부르는 법

프로그램은 이 문서 폴더에서 두 단계 위의 `bin/hb.py`다.

```
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> baseline --work <작업 이름>
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> check --work <작업 이름> --task <번호> --phase red
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> check --work <작업 이름> --task <번호> --phase green
<파이썬> <하네스 폴더>/bin/hb.py --repo <제품 저장소> done --work <작업 이름> --task <번호>
```

- `<파이썬>`은 이 프로그램을 돌리는 파이썬이다. 검사 계약의 `runner`가 pytest면 그 저장소의 테스트가 도는 파이썬이어야 한다(모르면 사용자에게 한 번 묻고 `INDEX.md`에 적어 둔다). 아니면 아무 python3이면 되고, 테스트는 계약의 `command`로 돈다.
- 출력의 마지막 줄은 JSON 한 줄이다. `verdict`가 판정이다.

| verdict | 뜻 | 지휘가 할 일 |
|---|---|---|
| `ok` | 받아들임 | `summary`를 진행표에 그대로 적고 다음으로 |
| `stop` | 규칙에 걸림 | `reason`을 읽고 아래 "멈췄을 때"대로 |
| `not_run` | 검사가 실행되지 않음 | 통과가 아니다. 환경이나 명령을 확인한다 |
| `timeout` | 제한 시간을 넘김 | 통과가 아니다. 사용자에게 알린다 |

- `baseline`과 `check --phase green`은 전체 검사를 돌리므로 몇 분 걸린다. 셸 도구의 제한 시간을 넉넉하게 주어 앞에서(foreground) 돌린다. 도구의 최대 제한 시간보다 오래 걸릴 때만 백그라운드로 돌리고, 끝났다는 알림을 받기 전에는 다음 단계로 넘어가거나 턴을 끝내지 않는다.

## 시작할 때

1. 작업 브랜치에 있는지, `INDEX.md`의 상태가 "확정"인지 본다. 아니면 멈춘다.
2. 작업 폴더에 `state.json`이 이미 있으면 바탕 검사를 하지 않는다. 앞에서 끊겼거나, 평가나 검수가 할 일을 더한 경우다. 진행표에서 "완료"가 아닌 첫 할 일부터 이어 간다. 바탕 검사를 다시 돌리면 완료 기록과 "원래 깨져 있던 것"이 지워지므로 프로그램도 두 번째 바탕 검사를 거절한다.
3. 처음이면 `baseline`을 돌린다. 작업 트리에 커밋되지 않은 변경이 있으면 프로그램이 멈춘다. 그 변경은 건드리지 않고 사용자에게 알린다.
4. `baseline`이 `ok`면 `summary`("원래 깨져 있던 것 N건")를 `INDEX.md`에 적는다.

## 할 일 하나의 순서

1. **테스트 쓰기.** 구현자를 부른다. 할 일 본문의 경로와 테스트를 돌리는 명령(검사 계약의 `runner`에 맞는 것)을 주고 "테스트만 쓰고 멈춘다"고 시킨다. 새 함수가 필요하면 빈 뼈대까지만 만들게 한다.
2. **실패 확인.** `check --phase red`. 테스트가 본문에서 실패해야 `ok`다. `ok`가 아니면 구현자가 테스트를 고치고 다시 받는다.
3. **테스트 읽기.** 검토자를 새로 부른다. 설명서, 할 일 본문, 테스트 파일, 실패 확인 기록(`checks/`)의 경로를 준다. "꼭 고칠 것"이 있으면 구현자가 테스트를 고치고 2번부터 다시 한다. "꼭 고칠 것"이 남아 있는 동안에는 4번으로 가지 않는다.
4. **구현.** 구현자를 부른다. "테스트는 이미 있고 실패 확인을 받았다. 테스트는 고치지 말고 구현만 한다"고 시킨다.
5. **통과 확인.** `check --phase green`. 프로그램이 넷을 본다: 실패했던 테스트가 통과하는가, 테스트가 그대로인가, 새로 깨진 것이 없는가, 바꿔도 되는 파일만 바뀌었는가.
6. **구현 검토.** 검토자를 새로 부른다. 설명서, 할 일 본문, 바뀐 파일 목록, 통과 확인 기록의 경로를 준다. 구현자의 "문제없음" 보고는 주지 않는다. 검토자는 명령을 실행하지 못하므로, 부르기 전에 지휘가 바뀐 내용을 파일로 떠서 그 경로도 준다: `git diff HEAD -- <이 할 일의 파일> > <작업 폴더>/logs/NN-impl-diff.log`. 이름을 `.log`로 끝내는 것은, 저장소에 따라 `logs/` 전체가 아니라 `.log`만 git 제외일 수 있어서다(바탕 검사 때 프로그램이 확인하는 것은 `.log`다). 새 파일은 여기에 나오지 않으니 바뀐 파일 목록으로 알린다.
7. **지적 반영.** "꼭 고칠 것"이 있으면 구현자가 고치고 5번과 6번을 다시 한다.
8. **커밋.** 아래 "커밋하는 순서"대로 한다.

검토자를 부르기 전과 후에 아래 세 명령의 출력이 같은지 본다. 다르면 검토 결과를 버리고 멈춘다. 셋째 줄은 아직 git에 없는 새 파일의 내용이 바뀌는 것을 본다(앞의 둘은 이것을 못 본다).

```
git diff HEAD | shasum
git status --porcelain
git ls-files -o --exclude-standard -z | xargs -0 shasum | shasum
```

## 커밋하는 순서

1. 저장소의 안내문이 정한 검증 명령 가운데 프로그램이 돌리지 않는 것(lint, build, 타입 검사, 검사 계약이 가리키지 않는 다른 빌드 구성의 테스트 등)을 돌린다. 프로그램은 검사 계약에 적힌 테스트만 돌린다. 고치는 옵션(`--fix` 등) 없이 돌리고, 하나라도 실패하면 커밋하지 않고 구현자에게 돌려보낸다(7번). 원래 깨져 있던 테스트가 있는 저장소에서는 이 명령도 실패로 끝나므로, 고치기 전에 한 번 돌려 두고 실패한 테스트 이름이 고치기 전과 같을 때만 새로 깨진 것이 없다고 본다. 종료 코드와 그 이름을 진행표에 적는다. 이 명령이 파일을 바꾸면 아래 `done`이 멈춘다.
2. `INDEX.md`에 이 할 일의 결과를 적는다(프로그램의 `summary` 그대로, 위 명령들과 종료 코드, 남은 "권장" 지적, 고쳐 다시 받은 횟수).
3. 이 할 일의 파일만 지정해서 올린다: `git add <파일> <파일>`. `git add -A`와 `git add .`은 쓰지 않는다.
4. `done`을 돌린다. `ok`가 아니면 커밋하지 않는다.
5. 작업 폴더를 올린다: `git add .harness/artifacts/work/<작업 이름>`. 그 저장소가 작업 폴더를 git 제외로 정해 두었으면 `done`이 올릴 것이 없다고 알려 준다. 그때는 올리지 않고(`-f`로 밀어 넣지 않는다), 그렇게 했다고 `INDEX.md`에 적는다.
6. 저장소의 커밋 메시지 규칙을 따라 커밋한다.

커밋 뒤에는 작업 폴더에 아무것도 쓰지 않고 다음 할 일로 간다. 합치기, 올리기(push), 배포는 하지 않는다.

## 운영 규칙 네 줄

1. 검사 결과는 이번 실행에서 새로 나온 것만 쓴다. 지난 실행의 결과를 옮겨 적지 않는다. 원래 깨져 있던 것과는 개수가 아니라 테스트 이름으로 견준다(프로그램이 한다).
2. 끊긴 뒤에는 지금 변경 상태(`git status`와 마지막 커밋)를 먼저 보고 이어 간다. 커밋되지 않은 할 일은 검사부터 다시 한다.
3. 사용자 파일은 커밋에 섞지 않는다. 로그는 git에 넣지 않는다.
4. 진행을 막는 지적은 "꼭 고칠 것"뿐이다. "권장"은 진행표에 적고 넘어간다.

## 그 밖의 규칙

- **통과 표시.** 원래 깨져 있던 검사가 있으면 "전체 통과"라고 쓰지 않는다. 프로그램의 `summary`("새로 깨진 것 없음, 원래 깨져 있던 것 N건")를 그대로 쓴다.
- **테스트 정정.** 구현 중에 테스트가 틀렸다는 근거가 나오면 구현자는 멈추고 보고한다. 지휘가 이유와 수정안을 사용자에게 보여 주고, 승인받으면 `INDEX.md`에 적은 뒤 1번부터 다시 한다. 할 일 하나에 두 번까지다.
- **세 번 제한.** 테스트를 고쳐 다시 받는 것(2번과 3번)은 할 일 하나에 합쳐 세 번까지, 지적 반영(7번)도 따로 세 번까지다. 지휘가 `INDEX.md`에 세어 적는다. 넘으면 멈추고 사용자에게 알린다.
- **쓰는 곳.** `.harness` 안에서는 이 작업의 작업 폴더에만 쓴다. `state.json`과 `checks/`는 프로그램만 쓴다.
- **범위 밖.** 설명서에 없는 일이 필요해지면 하지 않고 "막힌 곳"에 적은 뒤 사용자에게 묻는다.
- **결제, 권한, 개인정보, DB 구조 변경.** 설명서에 적혀 승인된 범위와 환경 안에서만 한다. `INDEX.md`에 그 승인이 없으면 멈춘다. 범위와 환경이 그대로면 다시 묻지 않는다. 범위, 환경, 위험이 달라지면 달라진 일을 하기 전에 고친 넷(영향, 범위와 환경, 확인 방법, 되돌리는 법)을 사용자에게 보여 주고 승인을 받는다. 승인받으면 진행하기 전에 `spec.md`의 넷과 영향받는 할 일 본문(바꿔도 되는 파일이 달라지면 `tasks.json`의 그 항목도)을 고치고, `INDEX.md`에 승인 날짜와 사용자의 승인 글을 적는다. 영향받는 할 일이 이미 시작됐으면 "할 일 하나의 순서" 1번부터 다시 한다. 앞의 검사 기록은 새 범위의 증거가 되지 않는다. 구현자와 검토자에게는 고친 설명서와 할 일 본문을 준다. 승인을 받아도 테스트, 검토, 평가, 검수는 그대로 거친다.
- **실제 DB, 데이터, 비밀값, 운영 환경.** 이 개발 흐름에서는 실행하지 않는다(마이그레이션 적용, 데이터 수정, 비밀값 열람이나 변경, 운영 배포 등). 개발 승인으로 허락되지 않고, 따로 승인을 받아도 위의 배포 금지와 구현자의 "하지 않는 것"은 그대로다. 필요하면 대상과 하는 일을 적어 사용자에게 따로 명시적으로 승인받고, 그 대상, 하는 일, 사용자의 승인 글을 `INDEX.md`에 적는다. 실행은 이 흐름 밖에서, 그렇게 따로 승인받은 방법으로 한다.
- **승인 기록.** 승인 글을 `INDEX.md`에 적을 때 비밀값과 접속 정보(비밀번호, 토큰, 접속 문자열 등)는 옮기지 않고 빼거나 가린다.

## 멈췄을 때

| `reason`의 내용 | 할 일 |
|---|---|
| 커밋되지 않은 변경이 있음 | 건드리지 않고 사용자에게 알린다 |
| 준비 단계 오류, 전부 건너뜀, 실패한 테스트가 없음 | 구현자가 테스트를 고친다 (세 번 제한에 셈) |
| 테스트가 바뀜 | 구현자가 테스트를 되돌리거나, "테스트 정정"대로 승인받는다 |
| 새로 깨진 테스트가 있음 | 구현자가 구현을 고친다. 테스트를 약하게 고치지 않는다 |
| 바꿔도 되는 파일 밖을 고침 | 그 변경을 되돌리게 하거나, 할 일의 범위를 고칠지 사용자에게 묻는다 |
| 실패 확인 뒤에 커밋이 생김 | 멈추고 사용자에게 알린다 |
| 통과 확인 뒤에 코드가 바뀜 | 5번부터 다시 한다 |

## 끝나면

모든 할 일이 커밋되면 사용자에게 보고한다: 끝낸 할 일, 프로그램의 판정 요약, 남은 "권장" 지적, 하면서 막힌 곳. 막힌 곳은 `INDEX.md`에도 적는다.

다음은 평가다. 사용자에게 **새 창에서** 평가(`eval`)를 부르라고 알린다. 이 세션은 구현 과정을 알고 있어서 평가를 하지 않는다.

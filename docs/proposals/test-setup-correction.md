# 제안: 준비 데이터만 잘못된 테스트 바로잡기

- 상태: 설계 제안. 이 문서는 구현을 담지 않는다. 구현은 이 제안이 받아들여진 뒤 hb 절차(계획 → 개발 → 평가 → 검수)로 따로 한다.
- 대상: `bin/hb.py`, `skills/dev/SKILL.md`, `README.md`

## 한 줄

일반 개발 절차는 그대로 둔다. 테스트의 **준비 데이터만** 잘못된 경우를 따로 다룬다. 고치기 전의 실패를 남기고, 고친 뒤 **같은 명령으로 같은 테스트**를 다시 돌린다. 독립 검토자가 실제 변경 내용을 보고 기대값과 검사 조건이 그대로인지 확인한다. 준비 데이터만 바로잡았는데 같은 테스트가 실패에서 통과로 바뀌면 인정한다.

## 지금 동작

- `check --phase red`(실패 확인)는 `test_globs`에 걸린 파일 전체와 확인 명령으로 지문(`test_fp`)을 만들어 남긴다.
- `check --phase green`(통과 확인)은 지금 지문이 실패 확인 때와 다르면 "실패 확인 뒤에 테스트가 바뀜"으로 멈춘다.
- 멈추면 개발 문서의 "테스트 정정"을 한다. 구현을 빼 두고 되돌린 뒤, 테스트 쓰기부터 다시 하고, 실패 확인을 새로 받는다.

## 문제

1. **실패 기록이 덮인다.** 실패 확인을 다시 돌리면 `state.json`의 그 할 일 항목이 새 기록으로 통째로 바뀐다. `checks/`의 파일은 남지만, 어느 기록이 어느 기록을 대신했는지는 상태 파일에 남지 않는다.
2. **준비 데이터의 잘못과 테스트 내용의 변경을 구별하지 못한다.** 테스트가 읽는 입력 파일의 오타나 실행 환경 설정의 누락처럼 기대값과 상관없는 잘못을 고쳐도, 단언을 바꾼 것과 똑같이 구현을 빼 두고 처음부터 다시 해야 한다. 이 비용 때문에 "테스트를 고치지 않고 우회하기"나 "실패를 억지로 다시 만들기" 같은 잘못된 길로 빠지기 쉽다.
3. **고친 것이 무엇을 바꿨는지 프로그램이 증거로 남기지 않는다.** 고치기 전에 실패했다는 것과 고친 뒤 통과했다는 것이 같은 명령, 같은 테스트, 같은 구현에서 나온 결과라는 기록이 없다.

이 문제는 특정 언어나 실행기의 문제가 아니다. 준비 데이터가 `test_globs`에 걸려 있으면 pytest, jest, Gradle, xcodebuild 모두 같은 길을 탄다.

## 바꾸지 않는 것

- 일반 개발에서는 실패 확인 뒤에 테스트가 바뀌면 지금처럼 멈춘다. 이 제안의 기록이 없는 변경은 통과 확인이 지금처럼 거절한다.
- 완료 기준 문장이 바뀌는 정정은 지금처럼 사람 승인을 받고 테스트 쓰기부터 한다.
- 기대값이나 검사 조건이 바뀌는 정정은 지금의 "테스트 정정"으로 한다.
- 통과 확인의 나머지 관문(실패했던 테스트의 통과, 새로 깨진 것 없음, 바꿔도 되는 파일만 바뀜)과 `done`, `review`의 판정은 그대로다.
- 프로그램은 뜻을 판단하지 않는다. "준비 데이터뿐인가"는 사람과 검토자가 본다.

## 용어

- **준비 데이터**: 테스트가 검사하기 전에 상황을 만드는 데 쓰는 것. 입력 파일, 가짜 객체가 돌려주는 값, 공용 준비 코드, 테스트 실행 환경 설정(환경 변수, 시간대, 임시 폴더 등).
- **기대값**: 테스트가 "맞다"고 보는 값. 단언의 비교 대상, 기대 출력 파일(golden, snapshot), 기대 오류.
- **검사 조건**: 무엇을 얼마나 엄격하게 보는지. 단언의 종류와 허용 오차, 건너뛰기·재시도·실패 예상 표시, 제한 시간, 테스트의 이름과 개수.

어느 쪽인지는 **파일 이름이나 폴더로 정하지 않는다.** `fixtures/` 아래의 기대 출력 파일은 기대값이고, 테스트 파일 안의 준비 코드 한 줄은 준비 데이터일 수 있다. 실제로 바뀐 줄을 보고 정한다.

## 제안

### 1. 실패 확인 기록을 덮어쓰지 않는다 (일반 개발 포함)

실패 확인을 다시 받으면, 앞 기록을 `state.json`의 `tasks.<번호>.red_history` 끝에 그대로 옮기고 새 기록을 `red`로 둔다. 판정은 바뀌지 않는다. 기록만 남는다.

### 2. 준비 데이터 정정: 고치기 전과 고친 뒤를 프로그램이 돌린다

새 명령 하나를 두 단계로 쓴다. 이름은 가칭이다.

```
<파이썬> <hb>/bin/hb.py --repo <제품 저장소> setup-fix --work <작업> --task <번호> --phase before [-- <테스트 고르는 인자> ...]
<파이썬> <hb>/bin/hb.py --repo <제품 저장소> setup-fix --work <작업> --task <번호> --phase after
```

**before (고치기 전의 실패를 남긴다)**

- 이 할 일의 실패 확인 기록이 있어야 하고, 그 뒤에 커밋이 없어야 한다.
- 테스트 쪽 파일이 아직 바뀌지 않았어야 한다. 지금 지문이 마지막으로 인정된 지문(실패 확인 때의 지문, 또는 앞 준비 데이터 정정의 after 지문)과 같아야 한다.
- 테스트를 고르는 인자는 할 일의 `check_args`와 같은 꼴이다. 주지 않으면 `check_args`를 쓴다. 할 일 밖의 테스트가 준비 데이터 때문에 깨진 경우(예: 통과 확인의 전체 검사에서 발견)에는 그 테스트를 고른다.
- 고른 테스트 가운데 실패하거나 오류가 난 것이 하나 이상 있어야 한다. 원래 깨져 있던 것은 세지 않는다. 가져오기나 문법 오류는 코드의 문제이므로 지금의 실패 확인처럼 받지 않는다.
- 남기는 것: 실행한 인자, 고른 테스트 이름과 결과, `test_globs` 밖에서 바뀐 파일마다의 지문, 테스트 쪽 파일 전체의 git 트리 ID(아래 "변경 내용 남기기"), 기록 경로.

**after (같은 명령으로 같은 테스트를 다시 돌린다)**

- 인자를 받지 않는다. before가 남긴 인자를 그대로 쓴다. 그래서 같은 명령이 보장된다.
- before 뒤에 커밋이 없어야 하고, `test_globs` 밖 파일은 before 때와 바이트가 같아야 한다. 구현이나 설정을 함께 바꿨다면 테스트를 돌리지 않고 멈춘다.
- before 뒤에 바뀐 테스트 쪽 파일이 하나 이상 있어야 한다.
- 인정 조건(모두 만족해야 한다):
  - 고른 테스트 이름 목록이 before와 같다(늘거나 줄지 않았다).
  - before에서 실패하거나 오류가 났던 테스트가 모두 통과한다.
  - before에서 통과했던 테스트가 실패, 오류, 건너뜀으로 바뀌지 않았다.
- 인정되면 새 테스트 지문을 남기고, before와 after 사이의 실제 변경을 `logs/NN-setup-fix-<번호>.diff.log`로 남긴다. 출력에 바뀐 파일 목록과 그 경로를 낸다.
- 멈추면 before 기록은 그대로 둔다. 덮어쓰지 않는다.

**변경 내용 남기기.** before와 after 때 임시 인덱스 파일로 테스트 쪽 파일(git에 아직 없는 새 테스트 포함)을 git 트리로 적고(`GIT_INDEX_FILE=<임시> git add …` 뒤 `git write-tree`), 두 트리의 `git diff`를 남긴다. 사용자의 인덱스와 작업 트리는 건드리지 않는다. 테스트 파일을 통째로 복사해 두지 않으므로 큰 자원 파일이 있어도 기록이 커지지 않는다.

### 3. 통과 확인이 받아들이는 조건

통과 확인은 지금 지문이 실패 확인 때와 다를 때, 다음을 모두 만족하면 테스트가 바뀌었다고 멈추지 않는다.

- 마지막 실패 확인 뒤에 인정된 준비 데이터 정정이 있고, 그 after 지문이 지금 지문과 같다.
- 끝나지 않은 before(after가 인정되지 않은 것)가 없다.

그 밖의 경우는 지금처럼 멈춘다. 실패 확인을 새로 받으면, 그 전의 준비 데이터 정정은 기록으로만 남고 인정 근거가 되지 않는다.

### 4. 독립 검토

after가 인정되면 지휘는 검토자를 새로 불러 남겨 둔 변경(`…diff.log`)을 준다. 검토자는 **실제로 바뀐 줄**을 보고 다음을 확인한다.

- 기대값이 바뀌지 않았다.
- 검사 조건이 바뀌지 않았다(단언 약화, 건너뛰기·재시도·실패 예상 표시 추가, 허용 오차나 제한 시간 확대, 테스트 이름이나 개수 변경 없음).
- 바뀐 것이 준비 데이터뿐이다.

파일 이름이나 경로만으로 "준비 데이터"라고 인정하지 않는다. "꼭 고칠 것"이 나오면 준비 데이터 정정으로 인정하지 않는다. 그 변경을 되돌리거나, 지금의 "테스트 정정"으로 한다.

### 5. 개발 문서에 넣을 순서 (초안)

`skills/dev/SKILL.md`의 "테스트 정정" 옆에 둔다.

- **준비 데이터 정정.** 테스트가 준비 데이터 때문에 실패한다는 근거가 나오면 구현자는 멈추고 보고한다. 지휘가 근거를 읽고, 완료 기준 문장과 기대값과 검사 조건이 그대로일 것으로 보이면 이 갈래로 한다. 아니면 지금의 테스트 정정으로 한다.
  1. 지휘가 `setup-fix --phase before`를 돌린다. 구현은 빼 두지 않는다.
  2. 구현자에게 "준비 데이터만 고치고 멈춘다. 기대값, 검사 조건, 구현은 바꾸지 않는다"고 시킨다.
  3. 지휘가 `setup-fix --phase after`를 돌린다. `ok`가 아니면 구현자의 변경을 되돌리고 지금의 테스트 정정으로 한다.
  4. 검토자를 새로 불러 남은 변경을 준다(위 4). 검토자 앞뒤로 세 명령의 출력이 같은지 지금처럼 본다.
  5. "꼭 고칠 것"이 없으면 원래 하던 단계(통과 확인 등)로 돌아간다.
  - 한도: 테스트 정정과 합쳐 할 일 하나에 두 번까지.
  - 기록: `INDEX.md`에 이유 한 줄, before·after의 `summary`, 바뀐 파일 목록, 검토 결과를 적는다. 완료 기준 문장이 그대로이므로 사람 승인은 받지 않는다.
  - 고친 파일이 할 일의 바꿔도 되는 파일 밖이면 통과 확인이 지금처럼 멈춘다. 그때는 범위를 고칠지 사용자에게 묻는다.

"멈췄을 때" 표에 setup-fix의 멈춤 이유를 더한다.

## 예시

어느 프로젝트에서나 생길 수 있는 경우다.

**인정하는 경우**

| 실행기 | 잘못된 준비 데이터 | 고친 것 |
|---|---|---|
| pytest | 테스트가 읽는 `tests/data/orders.json`의 날짜가 이미 지난 날짜로 고정돼, 아직 유효한 주문을 만든다는 준비가 깨짐 | 날짜를 테스트 안에서 "오늘 + 7일"로 만들도록 준비 코드를 고침. 단언은 그대로 |
| jest | `__fixtures__/user.json`에 필수 필드가 빠져 준비 단계에서 오류 | 빠진 필드를 채움 |
| Gradle | `src/test/resources/application-test.properties`에 시간대가 없어 실행하는 컴퓨터에 따라 결과가 달라짐 | 시간대를 UTC로 적음 |
| xcodebuild | 테스트 묶음에 넣을 샘플 이미지가 자원 목록에서 빠져 파일을 찾지 못함 | 자원 목록에 더함 |
| 공통 | 테스트가 띄우는 하위 프로세스가 앞 실행의 캐시를 재사용해 바뀐 코드를 보지 못함 | 그 하위 프로세스의 환경 변수로 캐시를 끔 |

**인정하지 않는 경우** (지금의 테스트 정정으로 한다)

- `fixtures/expected_report.txt`(기대 출력 파일)를 지금 결과에 맞춰 고침. 폴더 이름이 fixtures여도 기대값이다.
- snapshot 파일 갱신.
- `assert total == 100`을 `assert total >= 90`으로 바꿈.
- 실패하는 테스트에 건너뛰기, 재시도, 실패 예상 표시를 붙임. 제한 시간을 늘림.
- 테스트를 지우거나 이름을 바꿈(after에서 고른 테스트 목록이 달라져 프로그램이 멈춘다).
- 준비 데이터를 고치면서 구현 파일도 함께 고침(after에서 프로그램이 멈춘다).

## 예외 상황

| 경우 | 결과 |
|---|---|
| 실패 확인 기록이 없는 할 일에 before | 테스트를 돌리지 않고 멈춤 |
| 실패 확인 뒤(또는 before 뒤) 커밋이 생김 | 테스트를 돌리지 않고 멈춤 |
| before 때 테스트 쪽 파일이 이미 바뀌어 있음 | 테스트를 돌리지 않고 멈춤. 고치기 전의 실패를 남길 수 없으므로 지금의 테스트 정정으로 |
| before에서 실패한 테스트가 없음 | 멈춤. 바로잡을 실패가 없음 |
| before에서 가져오기·문법 오류 | 멈춤. 준비 데이터가 아니라 코드 문제 |
| 끝나지 않은 before가 있는데 before를 또 돌림 | 멈춤. after를 먼저 끝내거나 변경을 되돌림 |
| before 없이 after | 멈춤 |
| after 때 테스트 쪽 파일이 하나도 안 바뀜 | 테스트를 돌리지 않고 멈춤 |
| after 때 `test_globs` 밖 파일이 다름 | 테스트를 돌리지 않고 멈춤. 다른 파일 이름을 낸다 |
| after에서 고른 테스트 목록이 다름 | 멈춤. 늘어난 이름, 줄어든 이름을 낸다 |
| after에서 before의 실패가 아직 실패 | 멈춤. 아직 실패하는 이름을 낸다 |
| after에서 통과하던 테스트가 나빠짐 | 멈춤. 그 이름을 낸다 |
| 실행 안 됨, 제한 시간 넘김 | 지금처럼 `not_run`, `timeout`. 인정 기록을 남기지 않는다 |
| 위의 모든 멈춤 | 앞의 기록(실패 확인, before)은 바뀌지 않는다 |

## 다른 프로젝트에서 쓸 수 있는가

쓸 수 있도록 설계했다.

- 비교 단위는 프로그램이 모든 실행기에서 이미 쓰는 **테스트 이름**이다. 실행기마다 다른 처리가 없다.
- 테스트를 고르는 인자는 각 저장소가 `check_args`에 쓰는 꼴 그대로다(pytest는 파일 경로, jest는 파일 경로, Gradle은 `--tests`, xcodebuild는 `-only-testing:`).
- 무엇이 테스트 쪽 파일인지는 각 저장소의 검사 계약(`test_globs`)이 정한다. hb에 특정 폴더 이름이나 파일 이름을 넣지 않는다.
- 변경 기록은 git만 쓴다. 저장소 밖의 도구나 실행 환경에 기대지 않는다.

## 알려진 한계

- 검토자가 실제로 변경을 보고 확인했는지는 프로그램이 확인하지 못한다. 지금의 테스트 읽기처럼 개발 문서의 순서와 `INDEX.md` 기록으로 지킨다.
- `test_globs` 밖에 있는 준비 데이터는 지금도 테스트 지문에 들어가지 않는다. 이 제안도 다루지 않는다.
- 준비 데이터를 고친 뒤 할 일의 테스트가 구현 없이도 통과하게 됐는지는 이 갈래에서 다시 확인하지 않는다. 기대값과 검사 조건이 그대로라는 검토로 대신한다. 이것이 걱정되는 경우는 지금의 테스트 정정(구현을 빼 두고 실패 확인부터)으로 한다.

## 구현할 때의 완료 기준 (초안)

구현 작업의 계획에서 다시 다듬는다.

| 번호 | 기준 | 확인 |
|---|---|---|
| C1 | 실패 확인을 다시 받으면 앞 기록이 `red_history` 끝에 그대로 남고, 판정은 지금과 같다 | 가짜 저장소에서 두 번 돌린 뒤 상태 파일을 읽는 테스트 |
| C2 | before는 위 "before"의 조건을 만족할 때만 기록을 남기고, 아니면 테스트를 돌리지 않거나 멈춘다 | 조건별 테스트 |
| C3 | after는 before의 인자로 돌리고, 위 세 인정 조건을 모두 만족할 때만 인정한다. 아니면 달라진 이름을 칸별로 내고 기록을 바꾸지 않는다 | 인정 1갈래 + 멈춤 갈래별 테스트 |
| C4 | after는 `test_globs` 밖 파일이나 커밋이 before와 다르면 테스트를 돌리지 않고 멈춘다 | 새 `checks/` 기록이 생기지 않음을 확인하는 테스트 |
| C5 | after가 인정되면 before와 after 사이의 테스트 쪽 변경(git에 없는 새 파일 포함)이 `logs/`에 남고, 사용자의 인덱스는 바뀌지 않는다 | 남은 변경 내용과 `git diff --cached` 전후 비교 테스트 |
| C6 | 통과 확인은 위 "통과 확인이 받아들이는 조건"일 때만 바뀐 테스트 지문을 받아들이고, 그 밖에는 지금처럼 멈춘다 | 인정된 정정 있음 → 통과, 없음 → 멈춤, 끝나지 않은 before → 멈춤, 정정 뒤 실패 확인을 새로 받음 → 앞 정정으로 통과 못 함 |
| C7 | pytest와 jest 가짜 실행기에서 C3의 판정이 같다 | 두 실행기의 테스트 |
| C8 | 기존 `tests/` 전체가 그대로 통과한다 | 전체 검사 |
| C9 | 개발 문서에 "준비 데이터 정정"의 조건, 순서, 한도, 기록이 있고, "멈췄을 때" 표에 멈춤 이유가 있다. README의 개발 설명에 한 줄 있다 | 문서 문장을 읽는 테스트 |

할 일은 셋으로 나눈다: 01 실패 기록 보존(C1, C8), 02 `setup-fix`와 통과 확인 조건(C2–C7), 03 문서(C9).

## 이번 제안에 없는 것

- 구현, 병합.
- 특정 제품 저장소의 코드나 테스트 수정.
- 구현을 빼 두지 않고 실패 확인을 다시 받는 방법(별도 작업 트리 등).
- 평가·검수 문서와 `review` 명령에서 준비 데이터 정정 기록을 따로 보는 것.

## 정할 것

1. 명령과 칸의 이름(`setup-fix`, `before`/`after`, `red_history`).
2. 한도를 테스트 정정과 합쳐 셀지, 따로 셀지. 이 제안은 합쳐서 두 번이다.
